Work on my existing browser-based JavaScript game, Survivor Island, in the current repository.

Start from the current main branch.

This is an existing game with substantial working systems. Do not rebuild the game, do not redesign the UI, and do not replace working Day 1, camp, conversation, strategy, challenge, idol, alliance, relationship, save/load, or Tribal Council systems unless a targeted compatibility fix is required.

Your task is to create the missing Season Engine / Episode Lifecycle foundation so the game can progress coherently beyond Day 1 and eventually support a full Survivor season.

Deliver this as one focused PR.

PRIMARY GOAL

Create one authoritative season-progression layer that answers:

* how many active players remain
* current day / round
* current tribe configuration
* pre-merge vs post-merge state
* when tribe swaps happen
* when merge happens
* which tribe or players are immune
* which tribe attends Tribal Council
* what happens when the player’s tribe is immune
* how non-player tribes eliminate someone
* when the game advances to the next round
* when the season enters endgame

The immediate goal is not to build the polished finale.

The goal is to make the overall season structure mechanically reliable enough that a game can progress from the starting cast through repeated eliminations, swap/merge, and toward the endgame without getting stuck or corrupting state.

KNOWN PROBLEMS TO VERIFY

These were identified during a code review of current main.

Verify them yourself before making changes.

1. Missing / broken tribe swap

GameManager.checkForMerge() appears to call something like:

shuffleTribes(2)

for a 3-tribe game at roughly 14 players, but a reliable implementation does not appear to exist.

Implement a safe tribe swap system.

The swap must:

* preserve every active survivor exactly once
* never reintroduce eliminated survivors
* preserve the player
* update each survivor’s tribeId / tribe metadata
* rebuild tribe member arrays correctly
* preserve relationship/trust/alliance data where appropriate
* create valid tribe names/colors
* safely initialize camp resources / water plan / relevant tribe state
* work with save/load
* emit an appropriate event
* only happen once unless explicitly configured otherwise

Do not hardcode it only for the current cast.

⸻

2. Other tribes currently do not eliminate players when the player’s tribe wins

A season cannot advance correctly if only the player’s tribe can attend Tribal Council.

When the player’s tribe wins immunity, determine which non-player tribe lost and perform an off-screen NPC Tribal Council simulation.

This should use existing game intelligence wherever practical:

* alliance membership
* trust
* relationships
* threat
* gameplay style
* strategy intent
* idols if safely supportable
* vote penalties if relevant

Do NOT expose hidden vote details to the player unless the game would logically reveal them.

At minimum:

* resolve one valid eliminated survivor
* record the elimination
* update tribe membership
* update survivor state
* update game history
* advance the round correctly

If the existing TribalCouncilSystem can be safely reused in a headless NPC mode, prefer reuse over duplicating voting logic.

If reuse would introduce player-specific UI assumptions, create a thin simulation layer around the same underlying logic rather than duplicating an entire Tribal system.

⸻

3. Challenge calendar has progression gaps

Current challenge configuration appears to have days that are missing, including around Days 8–9.

Also inspect ChallengeManager.getCurrentChallenge() for stale challenge state.

The game must NEVER silently reuse yesterday’s challenge because the current day has no challenge config.

Fix this.

Prefer a robust model where challenge selection can fall back based on:

* pre-merge vs post-merge
* number of active tribes
* active player count

rather than requiring every exact day to be manually hardcoded.

Do not overbuild challenge gameplay in this PR.

The goal here is valid challenge selection and season progression, not designing all new challenge mechanics yet.

⸻

4. Generic tribe challenges currently force player loss

Current generic TribeChallengeView appears to return something equivalent to:

playerTribeWon: false

when the user presses Complete Challenge.

Do not build the entire future Challenge Engine in this PR, but fix this enough that season progression is not deterministically broken.

Create a lightweight challenge resolver that can produce:

* winning tribe
* losing tribe
* playerTribeWon
* basic result metadata

Use existing survivor/tribe attributes plus bounded randomness.

Examples of reasonable inputs:

* physical ability
* mental ability
* teamwork
* health
* tribe size
* prior challenge performance if safely available

This should be structurally replaceable later by richer interactive challenges.

Preserve First Contact.

Do NOT downgrade First Contact to the generic resolver.

⸻

5. Merge lifecycle is too skeletal

Current merge behavior roughly flattens everyone into one tribe.

Upgrade this into a safe canonical merge transition.

At merge:

* merge exactly once
* combine all active survivors
* preserve eliminated players as eliminated
* update each active survivor’s tribe metadata
* initialize merged tribe aliases consistently
* preserve social systems
* preserve idols/inventory where appropriate
* mark isMerged
* emit merge event
* transition future challenges to individual format
* begin jury rules according to a centralized season configuration
* save correctly

Do not build an elaborate merge feast cinematic unless trivial.

Mechanics first.

⸻

6. Post-merge player elimination has conflicting state handling

Inspect eliminateSurvivor() and handleTribalCouncilComplete().

There appears to be conflicting behavior where the player may:

* be added to the jury
* trigger Game Over
* and then still continue through the day-advance path

Create ONE authoritative elimination outcome.

If the player is eliminated:

* stop normal playable progression for that player
* record the elimination correctly
* add to jury if jury has started
* transition to a safe game-over / eliminated state

Do not allow the eliminated player to return to camp as an active contestant.

Because the final Game Over experience is not the main focus of this PR, a minimal safe screen/state is acceptable if the existing one is incomplete.

ROUND / EPISODE LIFECYCLE

Create a clear canonical lifecycle.

Something conceptually like:

PRE_CHALLENGE CAMP

→ CHALLENGE

→ CHALLENGE RESULT

If player’s tribe is unsafe:

→ PLAYABLE STRATEGY

→ PLAYER TRIBAL

→ ELIMINATION

If player’s tribe is safe:

→ OPTIONAL SAFE-TRIBE CAMP EVENT

→ OFF-SCREEN NPC TRIBAL

→ NPC ELIMINATION

Then:

→ COMPLETE ROUND

→ CHECK SWAP

→ CHECK MERGE

→ ADVANCE DAY

→ RESET PHASE STATE

→ NEXT PRE_CHALLENGE CAMP

The actual implementation may differ to preserve current architecture.

But there must be ONE canonical round completion path.

Avoid multiple places independently doing:

day += 1

or resetting phase/timer.

Search for duplicate day advancement logic and consolidate where safe.

Be cautious: preserve working scripted Day 1 behavior.

⸻

SEASON INVARIANTS

Add explicit validation helpers.

At important transitions verify:

1. Every active survivor belongs to exactly one active tribe pre-merge.
2. No eliminated survivor exists in an active tribe.
3. No survivor exists in multiple tribes.
4. Player reference points to the canonical survivor instance.
5. Active survivor count equals the sum of active tribe member counts pre-merge.
6. Post-merge there is exactly one active merged tribe.
7. Every completed Tribal eliminates at most one contestant unless a special rule explicitly says otherwise.
8. Day / round advances exactly once.
9. Swap occurs at most once under the configured rule.
10. Merge occurs exactly once.
11. Player cannot remain playable after elimination.

Expose a development-only validation method such as:

seasonEngine.validateSeasonState()

Return useful diagnostics rather than silently failing.
